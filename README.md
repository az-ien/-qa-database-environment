# QA Database Environment

This repository provisions a disposable PostgreSQL 17 database, creates a `users` table, inserts exactly four dummy users, and validates that data with Python (pytest and psycopg), Java (TestNG and JDBC), and Playwright (TypeScript and node-pg).

Both suites run in one GitHub Actions job against the same PostgreSQL service. The database exists only for that job. GitHub removes the service container when the job finishes, which destroys the database and its data.

These credentials are for local development and CI only. Do not use them in production.

| Setting | Value |
|---|---|
| Database | `qa_test` |
| Username | `qa_user` |
| Password | `qa_password` |
| Port | `5432` |

## Architecture

```text
GitHub Actions job
        │
        ├─ postgres:17 service container
        │     database qa_test is created empty
        │
        ├─ sql/schema.sql
        │     creates public.users
        │
        ├─ sql/seed.sql
        │     inserts four users
        │
        ├─ pytest + psycopg
        │
        ├─ mvn test (TestNG + JDBC)
        │
        └─ Playwright + node-pg
              │
              └─ job ends → container and database are destroyed
```

There is no web application in this repository. The tests talk to PostgreSQL directly. The Playwright suite uses the Playwright test runner and does not open a browser page.

## PostgreSQL and seed data

`sql/schema.sql` creates `users`:

| Column | Definition |
|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY`, primary key |
| `name` | `TEXT NOT NULL` |
| `email` | `TEXT NOT NULL UNIQUE` |
| `status` | `TEXT NOT NULL` |
| `salary` | `INTEGER NOT NULL` |
| `created_at` | `TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP` |

`sql/seed.sql` inserts these four rows and uses `ON CONFLICT (email) DO NOTHING`, so running the script again does not create duplicate emails. Salaries are fixed values from 100 through 1000:

| Name | Email | Status | Salary |
|---|---|---|---|
| Maya Chen | `qa-test@example.com` | `active` | 480 |
| Luis Ortega | `inactive@example.com` | `inactive` | 125 |
| Priya Shah | `pending@example.com` | `pending` | 860 |
| Owen Blake | `admin@example.com` | `active` | 310 |

No other users are seeded.

## Python tests

`python-tests/test_database_users.py` uses pytest, psycopg 3, and expects. It checks that exactly four seeded users exist, that each email has its expected status, that Owen Blake exists, and that each returned salary is greater than 400. The count checks use `expect(...).to(equal(...))`. The Owen Blake check reads that user's row and uses `expect(row).to(contain("Owen Blake"))`. The salary check reads each full user row, uses `expect(len(rows)).to(equal(2))`, and uses `expect(row["salary"]).to(be_above(400))`.

A `connect` fixture opens `postgresql://qa_user:qa_password@localhost:5432/qa_test` and passes that connection into every test, then closes it. Query values are written directly in the SQL. Cursors are closed with context managers.

Python 3.12 is the version used in GitHub Actions.

## Java tests

`java-tests` is a Maven module on Java 17. `DatabaseUsersTest` checks the same four users and statuses as the Python suite. The Owen Blake check reads that user's row and requires the name column to be Owen Blake. The salary check reads each full user row, requires `salary` to be greater than 400, and requires exactly two rows. Query values are written directly in the SQL and executed with JDBC `Statement`. `@BeforeMethod` opens a connection before each test, and `@AfterMethod` closes it. Statements and result sets are closed with try-with-resources.

Maven Surefire runs the TestNG classes and writes XML reports to `java-tests/target/surefire-reports/`.

The Java tests connect with `jdbc:postgresql://localhost:5432/qa_test` as `qa_user`.

## Playwright tests

`playwright-tests/tests/users.spec.ts` uses the same four checks as the Python and Java suites. `playwright-tests/tests/database.fixture.ts` opens `postgresql://qa_user:qa_password@localhost:5432/qa_test` and passes that connection into every test, then closes it. Query values are written directly in the SQL.

`playwright-tests/playwright.config.ts` runs the `tests` folder on the Chromium project, retries twice on CI, and writes an HTML report to `playwright-tests/playwright-report/`. Traces are collected for every test. These tests do not open a page, so there is no application URL.

## Run locally

Install Docker, Python 3.12, JDK 17, and Maven. Start a temporary database:

```bash
docker run --name qa-postgres \
  -e POSTGRES_DB=qa_test \
  -e POSTGRES_USER=qa_user \
  -e POSTGRES_PASSWORD=qa_password \
  -p 5432:5432 \
  -d postgres:17
```

Wait until it accepts connections, then apply the schema and seed:

```bash
docker exec qa-postgres pg_isready -U qa_user -d qa_test
docker exec -i qa-postgres psql -U qa_user -d qa_test -v ON_ERROR_STOP=1 < sql/schema.sql
docker exec -i qa-postgres psql -U qa_user -d qa_test -v ON_ERROR_STOP=1 < sql/seed.sql
```

On PowerShell, pipe the scripts instead of using `<`:

```powershell
Get-Content sql\schema.sql | docker exec -i qa-postgres psql -U qa_user -d qa_test -v ON_ERROR_STOP=1
Get-Content sql\seed.sql | docker exec -i qa-postgres psql -U qa_user -d qa_test -v ON_ERROR_STOP=1
```

All three test suites connect to this container at `localhost:5432`, database `qa_test`, as `qa_user`.

Python:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r python-tests/requirements.txt
cd python-tests
pytest
```

PowerShell:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r python-tests\requirements.txt
Set-Location python-tests
pytest
```

Java, from `java-tests`:

```bash
mvn test
```

Playwright, from `playwright-tests`:

```bash
npm install
npx playwright test
npx playwright show-report
```

Remove the local database when you are finished:

```bash
docker rm -f qa-postgres
```

That command deletes the container and the data volume stored inside it.

## GitHub Actions

`.github/workflows/database-tests.yml` runs on:

- pushes to `main`, including merges, squash merges, and rebase merges
- manual `workflow_dispatch` runs

Pull requests do not start this workflow. The pipeline runs after the changes are on `main`.

The workflow has one job on `ubuntu-latest`. That job starts a single `postgres:17` service with a health check, checks out the code, installs the PostgreSQL client, and applies `sql/schema.sql` and `sql/seed.sql`.

It then installs Python 3.12 and the Python dependencies, runs pytest, sets up Temurin 17 and Maven, and runs `mvn test`. It then installs Node.js, runs `npm ci`, installs Playwright, and runs `npx playwright test`. The PostgreSQL service stays up for all three suites. A failure in one suite does not skip the others. The job still fails if setup, pytest, TestNG, or Playwright fails.

GitHub deletes the service container at the end of the job. There is no persistent database left behind, including when the job fails or is cancelled.

## Test reports

| Suite | Local path | Actions artifact |
|---|---|---|
| Python | `python-tests/reports/report.html` | `pytest-html-report` |
| TestNG | `java-tests/target/surefire-reports/emailable-report.html` | `emailable-report` |
| Playwright | `playwright-tests/playwright-report/` | `playwright-report` |

pytest writes a self-contained HTML report to `python-tests/reports/report.html`, and the same folder also contains the JUnit XML file. Surefire writes the full TestNG output locally, and the workflow uploads only `emailable-report.html`. Playwright writes its HTML report to `playwright-tests/playwright-report/`. The workflow uploads that report. All three artifacts are uploaded after the tests finish, including when a suite fails. Open the workflow run and download them from the Artifacts section.

Generated reports and Maven `target/` output are gitignored.

## Temporary database lifecycle

1. The workflow starts `postgres:17` with database `qa_test`.
2. `schema.sql` creates `users` in that database.
3. `seed.sql` inserts the four dummy users.
4. Python, Java, and Playwright tests read the same data.
5. The job ends and GitHub destroys the container, including the database files.

A later workflow run creates a new empty database and seeds it again. Nothing from the previous run is reused.

## Reuse the SQL from another repository

Copy `sql/schema.sql` and `sql/seed.sql`, or check this repository out and run them with `psql -f`. Point them at a database that the other repository provisions itself, or at a persistent PostgreSQL instance that the other project hosts.

This repository does not keep a database online after CI. Another project cannot connect to the database created by this workflow, because that database has already been destroyed.

Example against a database you manage:

```bash
psql "postgresql://USER:PASSWORD@HOST:5432/DATABASE" -v ON_ERROR_STOP=1 -f sql/schema.sql
psql "postgresql://USER:PASSWORD@HOST:5432/DATABASE" -v ON_ERROR_STOP=1 -f sql/seed.sql
```

Use that project's own credentials. Do not reuse `qa_user` / `qa_password` outside disposable test databases.

## Publish and run the workflow

This folder is already a git repository on `main`. The configured remote is:

```text
https://github.com/az-ien/-qa-database-environment.git
```

The GitHub repository name includes the leading hyphen. After reviewing the files, commit and push `main`:

```bash
git add .
git commit -m "Add disposable PostgreSQL setup and database validation tests."
git push -u origin main
```

The workflow starts on that push. You can also open the Actions tab, choose **Database Tests**, and run it with **Run workflow**.
